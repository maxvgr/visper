# Backend integration

Информация для backend-разработчиков по интеграции готовой frontend-вёрстки Visper с серверной частью.

Backend получает собранную вёрстку с готовыми HTML-страницами, CSS и JavaScript-файлами.

При интеграции желательно сохранять существующую HTML-структуру, классы и `data-*` атрибуты, так как они используются frontend-логикой и стилями.

---

# Формы

## Общая информация

Frontend уже отвечает за:

- клиентскую валидацию;
- обязательное согласие на обработку персональных данных;
- блокировку кнопки отправки до принятия обязательного согласия;
- отображение ошибок клиентской валидации;
- работу модальных окон;
- открытие окна успешной отправки формы.

Формы, подключённые к frontend-логике, имеют класс:

```html
<form class="form form-custom"></form>
```

Для форм с клиентской валидацией используется атрибут:

```html
data-validation
```

Поля, которые проверяются frontend, имеют:

```html
data-validate
```

Обязательные согласия имеют:

```html
data-privacy
```

Пока обязательный checkbox с `data-privacy` не отмечен, frontend блокирует кнопку отправки.

Backend должен повторно проверять обязательные поля и согласие пользователя независимо от клиентской проверки.

---

# Отправка форм

В production frontend самостоятельно заявку на сервер не отправляет.

Backend может использовать:

- обычную HTML-отправку;
- AJAX;
- API;
- отправку в CMS;
- отправку в CRM.

При обычной отправке можно добавить форме необходимые:

```html
action="/..." method="post"
```

При этом желательно не удалять существующие классы и `data-*` атрибуты формы.

На стороне backend также необходимо реализовать необходимые для проекта:

- серверную валидацию;
- CSRF-защиту;
- CAPTCHA / anti-spam;
- защиту от частых повторных запросов;
- отправку писем;
- передачу заявки в CRM / CMS;
- логирование ошибок.

Frontend-валидация не заменяет серверную.

---

# AJAX и успешная отправка

Если форма отправляется через AJAX, после получения от сервера подтверждения успешной обработки заявки необходимо вызвать:

```js
window.dispatchEvent(
  new CustomEvent("formSuccess", {
    detail: { form },
  }),
);
```

где `form` — DOM-элемент успешно отправленной формы.

Например:

```js
const form = document.querySelector(".form-custom");

fetch("/api/form/", {
  method: "POST",
  body: new FormData(form),
})
  .then((response) => {
    if (!response.ok) {
      throw new Error("Ошибка отправки формы");
    }

    return response.json();
  })
  .then(() => {
    window.dispatchEvent(
      new CustomEvent("formSuccess", {
        detail: { form },
      }),
    );
  });
```

Frontend после события самостоятельно закроет текущее модальное окно и откроет окно успешной отправки, указанное у формы:

```html
data-success-modal="success"
```

При необходимости имя окна можно передать явно:

```js
window.dispatchEvent(
  new CustomEvent("formSuccess", {
    detail: {
      form,
      successModal: "success",
    },
  }),
);
```

`formSuccess` необходимо вызывать только после подтверждения успешной обработки данных сервером.

Не вызывать событие сразу после начала HTTP-запроса.

---

# Ошибки при AJAX-отправке

Frontend автоматически выводит ошибки собственной клиентской валидации.

Автоматическая обработка серверных ошибок отдельных полей пока не предусмотрена.

Например, ответ:

```json
{
  "errors": {
    "user_email": "Некорректный адрес электронной почты"
  }
}
```

сам по себе не будет автоматически выведен около соответствующего поля.

Если для проекта потребуется вывод серверных ошибок непосредственно у полей, необходимо согласовать формат ответа и добавить соответствующую frontend-обработку.

# Текущие формы

## Форма «Напишите нам»

Поля формы:

```text
user_name
user_email
user_message
privacy
subscribe
```

Назначение:

- `user_name` — имя пользователя;
- `user_email` — email;
- `user_message` — сообщение;
- `privacy` — обязательное согласие на обработку персональных данных;
- `subscribe` — необязательное согласие на рекламно-информационные рассылки.

---

## Форма обратного звонка

Поля формы:

```text
user_name
user_phone
captcha
privacy
marketing
```

Назначение:

- `user_name` — имя пользователя;
- `user_phone` — телефон;
- `captcha` — CAPTCHA;
- `privacy` — обязательное согласие на обработку персональных данных;
- `marketing` — необязательное согласие на рекламно-информационные рассылки.

---

# Имена полей

На текущем этапе в разных формах есть отличающиеся названия одинаковых по смыслу полей:

```text
user_message / message
subscribe / marketing
```

При интеграции необходимо ориентироваться на фактический атрибут `name` поля в HTML конкретной формы.

Не переименовывать поля только на backend без соответствующего изменения HTML.

Если понадобится унификация имён, её необходимо согласовать с frontend.

---

# CAPTCHA

В собранной тестовой вёрстке CAPTCHA является заглушкой и не должна считаться production-защитой.

Настоящая CAPTCHA / anti-spam проверка должна выполняться сервером.

Backend может заменить тестовый механизм на используемую в production CAPTCHA, сохранив при необходимости существующую структуру формы.

После подключения реальной CAPTCHA тестовая заглушка может быть удалена.

# Yandex Maps API

## Общая информация

Секция «Контакты» использует Yandex Maps JavaScript API v3.

Frontend-код карты ожидает наличие глобального объекта:

```js
window.ymaps3;
```

Если API карты не подключён, блок просто не инициализируется.

Сам собранный JS карты API-ключ не создаёт и не получает.

---

## Текущая тестовая конфигурация

На этапе разработки используется бесплатный Yandex Maps API, настроенный для временного тестового домена проекта.

Это временная конфигурация.

Перед запуском production необходимо:

1. определить окончательный боевой домен;
2. проверить настройки API-ключа;
3. разрешить использование ключа на production-домене либо создать отдельный production-ключ;
4. проверить актуальные лимиты и условия Yandex Maps API;
5. проверить карту непосредственно на боевом домене.

Если оставить ограничения только на временный домен, после переноса сайта карта может перестать работать.

---

# Подключение Yandex Maps

Yandex Maps API должен быть подключён на странице до выполнения frontend-кода карты.

Пример:

```html
<script src="https://api-maps.yandex.ru/v3/?apikey=YANDEX_MAPS_API_KEY&lang=ru_RU"></script>
```

Способ хранения и подстановки ключа определяется backend / CMS проекта.

Ключ рекомендуется получать из конфигурации проекта, а не вручную прописывать в каждом шаблоне.

Следует учитывать, что ключ браузерного JavaScript API будет виден посетителю сайта через HTML / Network.

Поэтому ограничение использования ключа должно быть настроено в кабинете Yandex по разрешённым доменам.

# Настройки карты

Сейчас карта использует координаты офиса:

```text
30.3718, 59.9564
```

Если адрес компании изменится, необходимо одновременно проверить координаты карты.

Если контактная информация будет храниться в CMS, рекомендуется хранить отдельно:

```text
longitude
latitude
```

и передавать готовые координаты в frontend.

Получать координаты из текстового адреса непосредственно в браузере не требуется.

# Важно сохранить при интеграции

Frontend JavaScript использует следующие классы и атрибуты:

```text
.form-custom
data-validation
data-validate
data-privacy
data-success-modal
```

Не удалять и не переименовывать их без необходимости.

Также желательно сохранять существующие классы элементов форм и интерактивных блоков, так как они используются CSS и JavaScript.

Если backend существенно меняет HTML-структуру интерактивного компонента, после этого необходимо проверить работу frontend.

# Карта регионов поставки

В секции «Работаем по всей России» точки на карте уже расположены frontend-разработчиком.

Координаты существующих точек менять не нужно.

Пример пустой точки:

```html
<button class="about-regions__point" style="--point-x: 43.0244%; --point-y: 32%;" type="button" aria-label="Регион поставки"></button>
```

Чтобы добавить данные региону, необходимо использовать уже существующую точку с нужными координатами и добавить ей:

```text
data-region
data-value
data-label
```

Также необходимо заменить `aria-label` на название региона.

Пример заполненной точки:

```html
<button class="about-regions__point" style="--point-x: 62.5366%; --point-y: 77.8537%;" type="button" data-region="Амурская область" data-value="52" data-label="Вакуумных контактора" aria-label="Амурская область"></button>
```

Назначение данных:

- `data-region` — название региона;
- `data-value` — числовое значение;
- `data-label` — подпись к значению;
- `aria-label` — название региона для accessibility.

Frontend самостоятельно выводит эти данные во всплывающей подсказке при взаимодействии с точкой.

Не создавать новую точку путём копирования другой точки, если нужная позиция уже присутствует на карте.

Не изменять:

```text
class="about-regions__point"
--point-x
--point-y
```

без согласования с frontend, так как эти значения отвечают за расположение точки на карте.

Если количество регионов изменяется, необходимо также обновить текст счётчика секции, например:

```text
[ 12 регионов поставки ]
```
